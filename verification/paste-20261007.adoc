== Ordinary paste traversal

`ClipboardCommands.paste` routes untransformed, unmasked pastes through `place`,
which calls `Clipboard.paste`. That method iterates the clipboard directly.
`DiskOptimizedClipboard` inherits `LinearClipboard.iterator`, which selects YZX
order: a horizontal layer is traversed before proceeding upward.

`SingleThreadQueueExtent` now spills its oldest pending chunk when its bounded
capacity is reached. If a layer spans more chunks than that capacity, the next
layer revisits chunks already submitted. Each revisit repeats admission, scheduling,
native-write and history work. Increasing capacity would conceal this interaction
by retaining more chunks; it is not the proposed repair.

A FIFO simulation of the source traversal with these dimensions and production's
48-chunk capacity produces 12,096 submissions for an aligned 224-chunk footprint,
versus 224 for complete destination-chunk traversal. This is an algorithmic count,
not a measured native submission count or a promised 54-fold speed improvement.
Destination offsets can change the footprint.

== 26.10.1 traversal fix

Ordinary cuboid paste traversal now partitions the destination footprint into chunks
and translates each intersection back into source clipboard coordinates. Each chunk
is completed before the next is visited. The iterator is lazy and does not accumulate
the clipboard in memory. Non-cuboid clipboards retain their original membership and
iteration; clipboard storage order and transformed paste logic are unchanged.

Four offset/aligned traversal cases failed against the original implementation and
passed after the change. Additional tests cover source payload identity, air filtering,
biomes, entity offsets and flags, non-cuboid membership, and cancellation propagation.
The full build passed 250 core/Bukkit tests.

The native probe now supports the ordinary command's direct `Clipboard.paste` path.
Against the deployed 26.10.0 JAR, its guard detected a repeated destination chunk and
failed before completing the paste. Against the fixed candidate, with a four-chunk
queue and destination minimum `(28673,96,-28675)`, both pastes prepared exactly 240
distinct chunks without revisits. Paste execution, including queue/history completion
but excluding the subsequent verification scan, took 41,363 ms and 35,847 ms on this
constrained fixture. No full-duration old direct-paste benchmark was run, so these
measurements do not establish a numerical production speedup.

Both complete paste/undo cycles matched every block and exactly 1,267,224 audit rows.
The cancellation test retained 12,288 completed blocks with equal history/audit counts;
undo restored the region and brought the audit count to 24,576. The difference from
the earlier 8,192-block cancellation runs is the number of concurrently accepted chunks,
not lost or duplicated data. The final marker was `INCIDENT_PROBE_PASS`.

Queue capacities, admission timeouts, CoreProtect logging and cancellation semantics
were not relaxed. This fixes the demonstrated ordinary-paste traversal regression,
not arbitrary third-party integration failures or all sources of database latency.
The stale QuickShop handler and configured delayed packet policy remain separate.

Local evidence is retained under `build/paste-20261007`: baseline and candidate
server logs, worker snapshots, and build output. Schematics, third-party binaries,
and private server logs are not part of the source change.
